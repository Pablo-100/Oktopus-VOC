The bug you actually hit

lib/db.ts memoizes the database migration in a module-level variable so it only runs once per server instance. It never accounted for that one run failing.

Every route that reads or writes data calls initDb() first — CVEs, 0-days, assets, triage, metrics, exposure, GreyNoise. One shared fix covers all of them.

Everything found & fixed

Found while tracing the reported error — not a general audit, just what surfaced by following this one bug to its root.

SeverityWhereIssueFix
High lib/db.ts A single transient DB connection failure permanently broke every route for the life of the server process — not just the one request that hit it. fixed Reset the cached migration promise on failure so the next request retries cleanly.
Medium app/dashboard/page.tsx Error banner blamed "NVD rate-limits" on every failure, but this fetch (/api/cves) is 100% database-backed and never calls NVD — the advice was always wrong for this path. fixed Rewrote the message to describe the real failure domain and point at the existing 60s auto-retry.
Medium app/api/zero-days/route.ts Returned raw (e as Error).message straight to the client on failure — an infra/stack leak, and on a public, unauthenticated endpoint specifically. fixed Switched to apiError(), the project's own sanitizing helper already used everywhere else.
Low app/api/assets/route.ts Same raw-error-message leak in all three handlers (GET/POST/DELETE) — lower severity since this route requires login, but still against the project's own documented rule. fixed Same apiError() fix, all three handlers.
